# Data Model Plan

Status: draft for review (2026-10-07). Table-by-table plan for AKR-TMS's own PostgreSQL database. Phase files give
the copy-paste SQL; this document fixes names, columns, keys, partitioning, retention class and grants. Sources:
research files 25 (canonical model, s.13), 28 (alerts and cases, s.16.2), 22 (name records, s.13.3), 30 (access
events s.9.2, retention s.12.3), 23 (reporting), 26 (rating), 27 (scenarios), 29 (governance), and the DBS
DATA-MODEL.md (conventions, audit, jobs).

---

## 0. Conventions

- **Primary keys**: UUIDv7, time-ordered, generated by the application (`uuid` crate). `id uuid primary key` with **no
  database default** (never `gen_random_uuid()`; the research sketches that use it are superseded here).
- **Timestamps**: `timestamptz`, always UTC. `created_at` default `now()` everywhere; `updated_at` maintained by the
  application, on mutable tables only. A source's local timestamp is kept as read in `source_local_ts text` (ISO 8601
  without zone, as read; no column is `timestamp without time zone`, DR-87) beside the converted value.
- **No hard deletes** in domain tables (status or archived flags). The only deletes are retention jobs (section 18),
  which never touch `audit` tables.
- **Foreign keys**: always indexed; `on delete restrict` (nothing cascades in a bank). Across partitioned facts, the
  key includes the partition column.
- **Enums**: Postgres enums for closed sets (job status, case status, tier, verification level); `text` + `check`
  where the set may grow or is bank data (reason codes, transaction types; validated against reference tables).
- **Money**: `amount numeric(28,6)` always positive, with `dr_cr char(1)` where direction matters, `currency
  char(3)`, `amount_lcy numeric(28,6)`, `amount_usd numeric(28,6)`, `rate_source text`, `rate_date date`. IQD's minor
  unit as found in the CBS is recorded per source. Balances (`balance_snapshot`) are signed and exempt from the
  always-positive rule. `currency` is filled only through a bank-approved code map from the CBS's own currency code
  to ISO alpha (`code_maps` kind `currency`), checked by hand; a CBS ISO column is never copied (the ICS BANKS
  installation studied had wrong ISO numbers for EUR and LBP and a second dinar code). An unmapped currency code
  quarantines the row and never defaults to IQD (DR-36, D21).
- **i18n strings**: `jsonb {ar, en}` for admin-defined labels (branch names, reason codes, templates); `ku` added in P3.
- **Optimistic locking**: `version int not null default 1` on every mutable aggregate (cases, tasks, change requests,
  mappings, scenarios, reports, settings), compared through `If-Match`.
- **Lineage** (canonical tables, `[lineage]` below): `source_id uuid, source_table text, source_pk text,
  source_version text null, row_hash bytea, batch_id uuid, extracted_at timestamptz, mapping_version_id uuid`.
- **Source keys and sentinels**: a source key is a tuple; `source_pk` holds its parts joined by `|` in the order the
  mapping document lists them (DR-41; for example `BRA_CODE|CUS_NUM` for a branch-scoped customer key). A sentinel
  date (0001-01-01, 9999-01-01 and the like) is never stored as a real date: the mapping's `not_placeholder_date` rule
  (DSL.md B.5) sets a flag or quarantines. An unmapped code becomes `unknown` with a data-quality issue (DSL.md B.7),
  never a default. A source column that is constant, sentinel-only or at least 95% null is unpopulated (DR-38) and
  maps to null with its `field_availability` grade, never to a value such as "no" or 0.
- **Bi-temporal** (slowly changing canonical entities, `[bitemp]`): `valid_from date, valid_to date null,
  recorded_from timestamptz, recorded_to timestamptz null`. Facts (transactions, messages) are immutable once settled;
  corrections arrive as new rows linked to the original. Whether a source changes settled rows in place is checked,
  not assumed: a canonical row whose source `row_hash` changes under the same key is not overwritten; the change opens
  a `dq_issues` row and the new version stays in `raw` (DR-37). Status changes a source makes after creation (for
  example on outgoing transfers) are kept as events or versions, never overwrites.
- **Classification**: every column carries a data-classification tag (public, internal, personal, financial,
  detection-logic, secret-str, card) in `admin.column_classification`; it drives masking, field encryption and policy.
- **Field encryption**: personal columns marked `enc` hold AES-GCM ciphertext under a data key wrapped by OpenBao;
  searchable identifiers have a keyed-hash twin marked `hk` (HMAC-SHA256 under the match-key) so matching works
  without decryption.
- **Retention class**: every table names its class R1-R13 (ARCHITECTURE.md section 17); the retention engine reads
  `admin.retention_assignment`.
- **Partitioning**: high-volume facts range-partitioned by month (`booking_date`, `created_at` or `occurred_at`);
  raw landing by extraction day; partitions created ahead and dropped by the `partition_maintenance` job (no
  `pg_partman`). BRIN on time columns, B-tree on access paths, GIN only where a search needs it.
- **Schemas**: `raw`, `canon`, `feat`, `scn`, `alert`, `casework`, `kyc`, `ref`, `rpt`, `assess`, `audit`, `admin`.
  The case schema is `casework`, not `case`: CASE is a reserved word in PostgreSQL (docs/plan/research.md DR-20).
- **No reserved words as identifiers**: no schema, table or column is named with a PostgreSQL reserved word (`case`,
  `default`, `grant`, `limit`, `references`, `window`, `user`, `order`, ...); a CI check parses every migration
  against the reserved-word list (DR-20).
- **Roles and grants** (section 20): `akr_app`, `akr_ingest`, `akr_assess`, `akr_audit_writer`, `akr_readonly`,
  `akr_migrate`, and `akr_retention` (phase 23, the only deleting role). Grants are listed table by table; never `ALTER DEFAULT PRIVILEGES`. No role has UPDATE or DELETE on
  `audit` tables or on append-only event tables.

Column shorthand below: `pk` primary key, `fk` foreign key, `null` nullable, `[std]` = `created_at, updated_at,
version`.

Mapping rules from the CBS discovery (DR-36 to DR-42). The rules are general; the column names in parentheses are the
ICS BANKS installation studied (cbs-discovery/CBS-DISCOVERY.md) and live in that adapter pack's mappings, not here.

- **party**: `birth_date` and `established_on` are routed by the person/entity indicator, because one source column
  can hold a birth date for persons and an establishment date for entities (BIR_DATE by IND_CORP_FLAG). A 1 January
  date is stored with `birth_precision` unknown and a quality flag, since a year-only value cannot be told from a
  true 1 January birth. `pep_status` is never taken from a CBS PEP flag the bank has not declared maintained (DR-38);
  a CBS customer class such as "Political" is kept as a lead with its source for the PEP review, never as a status.
- **party_name**: one row per source name field. A short-name field is not used for screening when the full name
  lines are present. `maybe_truncated` is set when the value reaches the source's byte cap (measured on source bytes;
  30 bytes per line in the ICS BANKS installation studied); it raises a degraded flag and never lowers a match score
  (D21).
- **party_identifier**: a placeholder value (all zeros, all ones, 123456 and the like) sets `placeholder_flag` and
  leaves `value_hk` null so placeholders never match each other. A `value_hk` held by more than one party is not a
  unique match key; a match on it is a review candidate (DR-41). Sentinel and impossible expiry dates set `expires_on`
  null with `expiry_flag` impossible; a plausible expired date is kept with `expired`, never dropped (the KYC review
  queue reads it).
- **party_relationship**: `share_pct` is null when the source holds no ownership percentage; a test that needs one
  reports unknown, never 0, and raises a data-quality issue. Relation codes without a bank-confirmed meaning map to
  `unknown` with a data-quality issue (DSL.md C-50).
- **customer**: `channel`, `cdd_level` and `expected_profile` are null when the source does not hold them. A CBS
  expected-activity field that reads 0 or is empty is never mapped as "expected zero activity"; `expected_profile`
  stays null until the bank's KYC refresh supplies a declared value with its source and date, and a scenario reads it
  as a missing optional input (DSL.md `?`), never as zero or low. `feat.profiles.expected` is computed by AKR-TMS and
  is a different field. A customer record that is the bank itself (customer number 0 in every branch in the ICS BANKS
  installation studied) carries a quality flag until the bank confirms it; it is not dropped from screening.
- **account**: `status` comes through the `status` code map (ICS BANKS code list 5: 1 open, 2 closed, 3 dormant,
  4 stopped, 8 black listed, 9 deleted). `status_changed_on` is the source's last status-change date; `closed_on` is
  set from it only for the closed status and stays null for deleted or unconfirmed closes. `dormant_since` is derived
  by the engine from the last posting (the source's last-activity date checked against postings; a sentinel such as
  0001-01-01 means never used, giving null with a flag), never from the source dormancy status alone. Days are counted
  to the source business date (DR-39). Until the posting history is loaded, `dormant_since` stays null and dormancy
  scenarios degrade with a flag. `parent_account_id` stays null until the bank confirms a parent link exists.
- **account_party_role**: where the source keeps signers per customer rather than per account, the signer role is
  copied to each account of the holder with `derived` true; this fan-out is an assumption until the vendor confirms
  it. `party_relationship` type signatory carries the same source and must not diverge. `signing_rule` is null unless
  the signing fields are mapped.
- **account_hold**: court, CBI and AML types are set only when the bank's reason-code map gives them; otherwise the
  hold is block, restriction, stop_payment or other, and `authority` is null.
- **balance_snapshot**: `source` = `cbs_current` for the balance read on its business date; history is rebuilt from
  the running balance on postings (`rebuilt_from_postings`, with a flag), never by stamping today's balance on a past
  date. `available_balance` is null until a source column is confirmed. A negative balance on an account with no
  facility is recorded in `dq_issues` and does not create a facility row.
- **txn keys**: `account_id` is null for a general-ledger leg (no customer account; about 9.5% of legs in the sample
  studied), which keeps its `ledger_code`. `document_key` groups the legs of one posting so each group can be tested
  for balance in local currency; it is provisional until the vendor confirms how documents are keyed.
- **txn money**: `amount` is the unsigned source amount in the account currency, the sign from the debit/credit
  indicator. `amount_lcy` is the source's own local-currency equivalent where it has one, and is the base for IQD
  thresholds (DSL.md T-04: IQD and USD thresholds stay separate). Where it differs from amount x rate by more than 1%,
  `rate_flag` is set and the value is not corrected. A leg with an unmapped currency is not valued in IQD; it scores
  high or carries a degraded flag (D21).
- **txn time**: `posted_at` stays null when the source has no dated timestamp (DR-37). A time-of-day column without a
  date is kept in `raw` and is not used for `posted_at` until the bank confirms its meaning. `source_local_ts` keeps
  the precision the source gives (`source_ts_precision`). Freshness and ordering use `business_date` (DR-39).
- **txn approval**: `authoriser_id` is set only when the source records an accepting approver (MAN_REP = 2); reject
  and suspend replies never fill it. A null authoriser means no approver was recorded, not that none was required,
  and it is never scored as approved. The monthly share of postings with an authoriser is a data-quality metric.
- **txn lifecycle**: `reverses_id` is set from the source's reversal pairing (same cancel reason, opposite direction,
  resolved original-key pointers); a self-pointing or unresolved pointer opens a `dq_issues` row and is never scored
  low. `corrected_by_id` stays null when the source has no correction link. For CBS legs `txn.status` is posted or
  cancelled; a posting still in a pending queue is not a txn row. `txn_event` kinds written from a CBS are `posted`
  (every leg; `at` = the actual booking date), `authorised` (accepting approver only), `cancelled` (cancel reason set)
  and `pending` (pending-queue rows, no history); `initiated` and `rejected` are written only from a source that logs
  them, never inferred.
- **txn cash and system flags**: `cash_flag` follows the mapping's cash rule (ICS BANKS: DIS_CODE = 1 with EXPL_CODE
  1 or 2); a cash-like leg with another code is kept with a review flag, never set false. `cash_event.ctr_flag` uses a
  threshold governed as bank data (D20). `system_generated` is set only from the bank-confirmed list of batch
  operators, programs or codes held in the mapping (DR-42), never from amount or narrative; until the bank confirms
  the list it is null, not false, and the readiness view shows the share of null-flag legs per month. Behavioural
  scenarios exclude flagged legs by default.
- **payment_message**: `format` stays (iso20022, mt); domestic and central-bank transfers are told apart by `rail`.
  Status changes the source makes after creation are kept as events, never overwritten; the message is immutable
  only after its final status. Rows that disappear between reads become delete events (DR-37), with a periodic full
  snapshot diff for deletions older than the re-read window. `uetr` is null when the source has none and is never the
  only match key.
- **payment_message_party and counterparty**: a missing name, account or BIC is stored null with a flag
  (missing_name, missing_account, missing_bic), scores high under D21, and is never an empty string. Source country
  codes in ISO numeric form are converted through a bank-approved code map (kind `country`).
- **cbs_user_activity**: logins and manager overrides come from the source's own logs where it has them. A CBS that
  keeps only the last updater of each row (no field-level trail) cannot show which operator changed a customer
  record, and this table does not claim to.

Joins (research file 25 s.13.3): party has names, identifiers, contacts; party-to-party relationships; party ->
customer -> account <- account_party_role -> party; account -> txn -> txn_event; txn -> counterparty, channel,
branch, product; txn <-> payment_link <-> payment_message -> payment_message_party; account -> balance_snapshot,
account_hold; card -> account; card_txn -> txn; staff -> party.

## 22. Sizing and growth (planning assumptions; discovery replaces them)

- `canon.txn` with indexes: about 300-600 bytes a row. One million postings a day for seven years (2.5 billion rows)
  is of the order of 0.7-1.4 TB with the raw layer; 100,000 a day is a tenth.
- Measured on the discovery snapshot (a mocked ICS BANKS on Oracle, not a bank's data): postings 1.04 GB for 5.42
  million rows (about 190 bytes a row, indexes not reported) over 7.3 years; 1,488 postings a business day on average
  over the last 90 days, 2,100 at the 95th percentile. The million-a-day figure is a planning figure for a larger
  bank. Raw sizing depends on the re-read window: only changed rows are landed (section 3).
- `audit.access_event`: 200 analysts at 500 views a day is about 100,000 rows a day, about 36 million a year.
- `feat.feature_values` dominates after `txn` when many features are kept per entity per day; R4 caps it at three
  years or the longest look-back.
- Lists: tens of thousands of entries; the in-memory index rebuild takes seconds.
- `wal_compression=zstd`; pgBackRest as in the DBS.
