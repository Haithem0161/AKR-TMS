| DR-29 | 2026-10-07 | A step-up assertion is an opaque UUIDv7 id whose ledger row binds it to the user, the Kratos session, one action class and optionally one resource; it is consumed by a conditional UPDATE inside the protected action's transaction. | DR-31 | 2026-10-07 | The BFF enforces the idle and absolute session limits: last activity in Valkey, touched only by mutations and an explicit heartbeat (never by GETs or the event stream); a missing key counts as expired, so a Valkey restart signs everyone out; the absolute limit counts from the Kratos session's issue time; Kratos's lifespan is only a ceiling | CBI 8.3.1 and 14.2.1 idle time-out; background polling must not keep an unattended screen signed in; failing closed is the safe direction (UX-35) |
| DR-32 | 2026-10-07 | The BFF refuses a TOTP code already used by the same identity within 90 seconds (Valkey `SET NX`), at sign-in and at step-up | Kratos accepts a reused code inside its window (DBS phase 01 s.8.12); NIST SP 800-63B 5.1.4.2 requires a time-based code to be accepted once |
| DR-33 | 2026-10-07 | One principal table: `admin.users` with kind human, service or system is the FK target of every actor column; one seeded system principal acts for jobs. The bootstrap CLI moves from phase 03 to phase 01 and creates the first ADM and the first SEC as two different people | FKs from the idempotency ledger and every later actor column; SP-16 (own identity, owner, expiry, last use); D7 (decisions are a person's act); phase 01 cannot be verified without a first user, and maker-checker needs two people |
