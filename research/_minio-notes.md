Reading for AKR-TMS: the community source as archived carries at least two unauthenticated-write flaws whose only precondition is a known access key (access keys are not secret by design in S3: they appear in logs and presigned URLs). In a WORM bucket a forged write cannot overwrite or delete a locked version, but it can plant new objects or versions, which defeats "the evidence store only contains what AKR-TMS wrote". The advisories describe each fix in prose (missing switch case; signature gate on query-string credentials; 128 KB line cap; replication-header check; getVolDir validation), enough to write independent patches without copying AIStor code.

### AGPL obligations (licence text from raw.githubusercontent.com/minio/minio/master/LICENSE; GPL FAQ via the Wayback Machine, gnu.org unreachable)
- AGPL section 13: "if you modify the Program, your modified version must prominently offer all users interacting with it remotely through a computer network (if your version supports such interaction) an opportunity to receive the Corresponding Source of your version by providing access to the Corresponding Source from a network server at no charge".
- AGPL section 5, aggregate: "A compilation of a covered work with other separate and independent works, which are not by their nature extensions of the covered work, and which are not combined with it such as to form a larger program ... is called an "aggregate" ... Inclusion of a covered work in an aggregate does not cause this License to apply to the other parts of the aggregate."
- GPL FAQ (#MereAggregation): "If the modules are included in the same executable file, they are definitely combined in one program ... By contrast, pipes, sockets and command-line arguments are communication mechanisms normally used between two separate programs. So when they are used for communication, the modules normally are separate programs. But if the semantics of the communication are intimate enough, exchanging complex internal data structures, that too could be a basis to consider the two parts as combined"; (#AggregateContainers) containers do not change the analysis.
- MinIO's own COMPLIANCE.md: "MinIO cannot make the determination as to whether your application's usage of MinIO is in compliance ... rely on your own legal counsel"; "MinIO Commercial Licensing is the best option for applications that trigger AGPLv3 obligations".
- Reading for AKR-TMS (for counsel to confirm): AKR-TMS reaches the store only over the standard S3 HTTP API with standard S3 semantics, runs it as a separate process and container, and links none of its code, so AKR-TMS is a separate program and an aggregate, not a derivative work. Obligations that do apply: (1) delivering the store's binary or image to a bank is conveying object code, so ship the Corresponding Source of the exact build (or a written offer) plus LICENSE, NOTICE and CREDITS (AGPL section 6); (2) if AKR-TMS adds its own patches, section 13 also applies: publish the patch branch and give each bank its source with the release. Neither obligation reaches AKR-TMS's own code.

### Object lock in the MinIO code line
- Silo's documentation (carried over from MinIO's): "COMPLIANCE lock is protected from write operations by *all* users, including the MinIO root user ... You cannot change or remove the lock before the configured retention duration has passed"; "functionally identical to the S3 COMPLIANCE mode"; lock can be enabled only at bucket creation; legal hold "protected from write operations by *all* users, including the MinIO root user", set and lifted only with s3:PutObjectLegalHold; versioned delete of a locked version is blocked, an unversioned delete only adds a delete marker; lifecycle rules can expire non-current versions only after retention or hold ends.
- Same page: "meets SEC17a-4(f), FINRA 4511(C), and CFTC 1.31(c)-(d) requirements as per Cohasset Associates". The Cohasset report (min.io/cohasset/introduction) assessed "MinIO Object Storage, Release 172, configured with Object Lock enabled and Object Lock mode set to Compliance, when on-premises, running on MinIO qualified hardware": an old, specific release; it shows the design is sound, it does not certify any 2026 build. Each AKR-TMS build must be re-proved with the WORM conformance suite.

- **Static key unseal** (2.4.0): "Add static key unseal mechanism to allow auto-unseal in environments with explicit trust chaining."
- **Auto-unseal as plugins** (2.6.0): new `kms` plugin type; 2.7.0: "The pkcs11, alicloudkms, awskms, azurekeyvault, gcpckms and ocikms seals are no longer built-in and must be installed as external plugins"; "Discontinue the HSM distribution of OpenBao ... PKCS#11 functionality remains available via the PKCS#11 KMS plugin". Transit seal stays built in.
- **External Keys** (2.7.0): "The PKI and Transit secret engines can now use KMS plugins to perform cryptographic operations without storing key material in OpenBao" (PKCS#11 via kms-pkcs11; transit-backed built in). Lets a bank keep AKR-TMS signing keys in its HSM.
- **Post-quantum** (2.7.0): ML-DSA (FIPS 204) in PKI and Transit; pure-PQC TLS key exchange options (X25519MLKEM768 etc.).
- Correction to file 32: "OpenBao has a namespaces working group" is out of date; namespaces shipped in 2.3.1.
