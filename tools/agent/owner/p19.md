### 7.21 RFI pre-fill from the replica, and the map it reads (owner decision 4; DR-417)
The desk gets proposed answers for an incoming correspondent RFI, computed from the product's own records, and a person records each one. What was missing is the map from a question key of the bank's template to a fact the product holds; it is now admin-managed data. M-44 is implemented. DR-422 locks the corrections of the check round of 2026-10-11: four sensitive sources, the PEP register as the first source of `party.pep_status`, and the purpose rule for the activity figures.

1. **The map** (extends DATA-MODEL s.12; the table is added to migration `0064_casework_followup_records.sql`, the guard, grants, classification and retention rows to `0065_casework_followup_guards_grants.sql`; owner `akr_migrate`, written by `akr_app`):

```sql
-- migration 0064_casework_followup_records.sql, added part
-- Phase 19 (owner decision 4, DR-417). Which fact of the product's records pre-fills which question key. Changed by change request only.
CREATE TABLE IF NOT EXISTS casework.rfi_prefill_map (
    id                  UUID PRIMARY KEY,
    question_key        TEXT NOT NULL CHECK (question_key ~ '^[a-z][a-z0-9_.]{2,80}$'),
    source_key          TEXT NOT NULL CHECK (source_key IN ('relationship.start_date', 'relationship.status', 'party.type',
                                                            'party.residence_country', 'party.pep_status', 'accounts.open',
                                                            'accounts.closed', 'accounts.signatories',
                                                            'activity.declared_and_actual', 'rating.cbi_level')),
    state               TEXT NOT NULL CHECK (state IN ('active', 'retired')),
    change_request_id   UUID NOT NULL REFERENCES admin.change_requests(id) ON DELETE RESTRICT,
    retired_by_request  UUID REFERENCES admin.change_requests(id) ON DELETE RESTRICT,
    created_by          UUID NOT NULL REFERENCES admin.users(id) ON DELETE RESTRICT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    retired_at          TIMESTAMPTZ,
    CHECK ((state = 'active') = (retired_at IS NULL)),
    CHECK ((state = 'active') = (retired_by_request IS NULL))
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_rfi_prefill_map_active ON casework.rfi_prefill_map (question_key) WHERE state = 'active';
CREATE INDEX IF NOT EXISTS idx_rfi_prefill_map_change_request ON casework.rfi_prefill_map (change_request_id);
```

```sql
-- migration 0065_casework_followup_guards_grants.sql, added part
-- A map row is changed once, when it is retired; a retired row never changes again, and no row is deleted.
CREATE OR REPLACE FUNCTION casework.rfi_prefill_map_guard() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'DELETE' THEN
        RAISE EXCEPTION 'pre-fill map rows are never deleted' USING ERRCODE = 'insufficient_privilege';
    END IF;
    IF OLD.state <> 'active' THEN
        RAISE EXCEPTION 'pre-fill map row is retired' USING ERRCODE = 'insufficient_privilege';
    END IF;
    RETURN NEW;
END $$;
DROP TRIGGER IF EXISTS trg_rfi_prefill_map_guard ON casework.rfi_prefill_map;
CREATE TRIGGER trg_rfi_prefill_map_guard BEFORE UPDATE OR DELETE ON casework.rfi_prefill_map
    FOR EACH ROW EXECUTE FUNCTION casework.rfi_prefill_map_guard();

GRANT SELECT, INSERT ON casework.rfi_prefill_map TO akr_app;
GRANT UPDATE (state, retired_at, retired_by_request) ON casework.rfi_prefill_map TO akr_app;

INSERT INTO admin.column_classification (schema_name, table_name, column_name, classification)
SELECT 'casework', 'rfi_prefill_map', c, 'internal'::admin.data_classification
FROM unnest(ARRAY['id', 'question_key', 'source_key', 'state', 'change_request_id', 'retired_by_request', 'created_by',
                  'created_at', 'retired_at']) AS c
ON CONFLICT (schema_name, table_name, column_name) DO NOTHING;

INSERT INTO admin.retention_assignment (schema_name, table_name, retention_class, clock, clock_column, note) VALUES
 ('casework', 'rfi_prefill_map', 'R9', 'retirement', NULL, 'RFI pre-fill map; retired rows are kept')
ON CONFLICT (schema_name, table_name) DO NOTHING;
```

2. **The source registry** (`PrefillSource`, a closed enum of `domain::casework::prefill`; the SQL CHECK of item 1 lists the same ten keys). A map row names a source, not a column: a bank cannot point a question at an arbitrary canonical field, and a source is added by a release. Every source is computed for the subject party of the RFI (`casework.rfis.party_id`) and returns typed `facts`:

| `source_key` | `facts` | Read through | Fits question format | Sensitive |
|-|-|-|-|-|
| `relationship.start_date` | `{ date }`: the earliest `onboarded_on` of the party's current `canon.customer` rows | `CanonPartyReader::current_customers` (the reader of phase 18; the method is added in item 4) | `value`, `free_text` | no |
| `relationship.status` | `{ records: [{ status, cdd_level }] }`, one per current customer row; no CIF | `CanonPartyReader::current_customers` | `value`, `free_text` | no |
| `party.type` | `{ type, legal_form?, established_on? }` of the current `canon.party` row | `CanonPartyReader` | `value`, `free_text` | no |
| `party.residence_country` | `{ iso2 }` | `CanonPartyReader` | `value`, `free_text` | no |
| `party.pep_status` | `{ answer, former? }`. The bank's PEP register decides first (view `kyc.party_pep_state`, phase 15): `pep` gives `yes`; `former_pep` gives `yes` with `former: true`; `candidate` gives `unknown`, because an unconfirmed lead is never stated. With no row, or the state `none`, the customer file decides (`canon.party.pep_status`): `pep` gives `yes`, `not_pep` gives `no`, anything else `unknown` | `PartyPepReader` (item 4), then `CanonPartyReader::current_party` | `yes_no_unknown`, `value` | no |
| `accounts.open` | `{ accounts: [{ type, currency, opened_on, status }] }`: the current accounts on which the party is `owner` or `joint` and `closed_on IS NULL`; no account number | `CanonPartyReader` | `value`, `free_text` | no |
| `accounts.closed` | `{ accounts: [{ type, currency, opened_on, closed_on }] }`: the same accounts with `closed_on` set | `CanonPartyReader` | `value`, `free_text` | yes (a closure can show an exit) |
| `accounts.signatories` | `{ parties: [{ role, name }] }`: the other parties with a current `joint` or `signatory` role on the accounts of `accounts.open`, each with its current `legal` name (`name_type = 'legal'`, `superseded_at IS NULL`; the Arabic or Kurdish form first). A party the caller may not see under phase 18 section 3.10 is left out, with no count and no flag | `CanonPartyReader::co_holders` (item 4) and `current_names` | `value`, `free_text` | yes (the names of other persons) |
| `activity.declared_and_actual` | `{ months: [{ period, currency, declared?, actual }] }` for the last three closed months | `ProfileQuery` of phase 13 with its `PartyProfilesView` projection (`actual`, `declared` and `status`; never a deviation, an own-history or a peer value), called with the caller's context and purpose code, so the Cedar check `profile.read`, the purpose rule and the access events of phase 13 section 3.6 apply as on the party page | `value`, `free_text` | yes (the profile is restricted data that the desk may not read) |
| `rating.cbi_level` | `{ cbi_level }`: the CBI label of the current rating (`high`, `medium` or `low`); absent when the party has no rating | `RatingSource::levels` (phase 13 port, phase 15 implementation), as the party page reads it | `value`, `free_text` | yes (the bank's own risk label) |

   Four of the ten sources are sensitive: `accounts.closed`, `accounts.signatories`, `activity.declared_and_actual` and `rating.cbi_level`. A sensitive source is computed for a caller with role M only (item 5 step 5). No source reads an alert, a case, a decision, a report, a watch, a hibernation, a screening hit, the exit register, an internal report or an authority request, and none ever will: the registry test of item 11 asserts it on the SQL that each source runs. Not in the registry in this version, and so typed by hand as before: source of wealth, beneficial owners, counterparty history, rating history with reasons, the last periodic review, screening and adverse-media history, linked documents and the respondent's comfort with the relationship (question 22 of the Wolfsberg list).

5. **`RfiPrefillService::proposals(ctx, rfi_id)`** (`GET /rfis/{id}/prefill`):
   1. Load the RFI under the visibility rule of section 3.2 (a suspicion RFI that the caller may not see is a masked 404, section 3.14); Cedar `rfi.prefill.read` on Rfi.
   2. The RFI has `kind = correspondent` and `direction = in`, and its status is `released` or `answered`; otherwise 409 `E_NOT_ALLOWED_IN_STATE`, sub-code `prefill_not_applicable`. The pack pinned to the RFI's case (`casework.policy_pack_version`, phase 17) has the switch `rfi.pre_fill` set to `true`; otherwise the same 409 with sub-code `prefill_off`.
   3. `X-Access-Purpose` holds a purpose code (422 `E_PURPOSE_REQUIRED` otherwise). This is a rule of this route at every tier, as the profile read of phase 13 has one; the phase 02 rule alone covers restricted and suspicion data only.
   4. Take the questions of the RFI in state `open` and the active map rows of their keys (`active_for_keys`). A question with no map row gives no proposal.
   5. For each pair: when the source does not fit the question's `answer_format`, `outcome = format_mismatch`; when the source is sensitive and the caller does not hold role M, `outcome = withheld` and the source is not computed; otherwise compute the source (item 2), with `outcome = empty` when it returns nothing and `proposed` otherwise. For `activity.declared_and_actual` a refusal by phase 13 (for the MLRO that is a purpose other than `investigation`) also gives `withheld`, and the other proposals of the response are not affected.
   6. `data_as_of` is the canonical batch time of the party row (phase 11 freshness, as phase 18 section 3.14 step 6).
   7. One access event `view` (resource `party`, the party's tier from `casework.effective_tier`, the purpose code) through the phase 02 access layer; the profile read of `activity.declared_and_actual` writes its own access events in phase 13, one per customer record. No audit row: the read changes nothing.

   Nothing is written to `casework.rfi_answers`. The desk person reads a proposal, edits the words and records it with `POST /rfis/{id}/answers` (section 3.3), with `source_kind = replica` and `source_ref = "prefill:<source_key>"`. The scan, the claim rules and the expiry of section 3.3 apply as to any answer, so every claim is still a person's act and `rfi.answer_recorded` is its record.

6. **`RfiPrefillService::propose(caller, PrefillMapChange)`** (`POST /rfi-prefill-map`):
   1. Shape: 1 to 100 entries in `set` and `remove` together; no question key twice across both lists; the key pattern of item 1. A failure is 422 `E_VALIDATION` with a JSON pointer to the entry.
   2. Each `set`: `source_key` is a key of the registry (sub-code `source_unknown`); `question_key` is a question of an RFI template of kind `correspondent` in the active policy pack (phase 09; sub-code `question_unknown`); the source fits that question's `answer_format` (sub-code `format_mismatch`). A `set` on a key with an active row replaces that row at activation.
   3. Each `remove` names a key with an active row (sub-code `not_mapped`).
   4. An open change request with `object_key = 'rfi_prefill_map'` gives 409 `E_NOT_ALLOWED_IN_STATE`: the map takes one change set at a time.
   5. Create the change request with phase 04 `ChangeRequestService::create` (origin Dedicated, so `submit` runs in the same transaction; kind `rfi_prefill_map`, `object_key` `rfi_prefill_map`, the caller's `reason_code` of family `change` and `reason_text`), route `cr_material`, volume effect `neutral`. The impact is `{set, removed, sensitive_sources}`, the last being the sensitive source keys in `set`.
   6. Respond 201 with the `ChangeRequestView`; `change_request.created` is written by phase 04.

7. **Change target `rfi_prefill_map`** (phase 04 `ChangeTarget`, registered in the registry, whose kinds are an open set; the route map gains no route): base class material, route `cr_material` (the MLRO and CHK, as for the policy pack whose templates the map extends), generic create no, emergency no, families `change`. `current_version` returns `None`. `prepare` runs steps 1 to 3 of item 6. `check_before_decision` runs steps 2 and 3 again against the pack that is active at the decision and returns the sub-codes as issues. `activate`, inside the approval transaction: for each `set`, retire the active row of the key if there is one and insert the new row as `active`; for each `remove`, retire the row; audit `rfi_prefill_map.applied`. `on_closed` with `Rejected` or `Withdrawn` writes nothing; there is no `revert`. `diff` shows the question keys and source keys before and after. The volume effect is always `neutral`: no scenario, rating or screening reads the map.

8. **Audit event** (one more row of section 3.12): `rfi_prefill_map.applied` on a `rfi_prefill_map` change applied; resource `rfi_prefill_map`; payload `{set, removed}` as lists of question keys; no case chain. The proposal writes `change_request.created` (phase 04). The pre-fill read writes an access event, not an audit row.
