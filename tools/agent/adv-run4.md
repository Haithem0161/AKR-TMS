# Adversarial pass, run 4 (clocks and timers on closed, merged or reopened items; Haiku draft for lead review)


### ADV-4-01 A manual grant that expires after its case is sealed appends a chain event to the sealed case   (verdict: FLAW; phase 18, with phase 00 timers)
- Rule: "A closed case is read-only (section 3.1 invariant I7)." (phase-18.md:852); phase 19 states the designed rule that follow-up records of a closed case "write their audit events and no case event, so the seal hash stays the hash of the chain at closure" (phase-19.md:1058); and the timer rule "it re-reads its owner and does nothing if the owner's state no longer calls for it (closed case, completed task, released freeze)" (phase-00.md:564-565).
- Attack:
  1. Analyst A2 `a2` holds `decide` on case C (open, outcome set). M grants a manual `work` access to `a1` with `expires_at` = now + 2 days (phase-18.md:1330-1331, a manual grant on a suspicion tier carries `expires_at`); the grant schedules timer `case_acl_expiry` at `fire_at = expires_at` (phase-18.md:1335-1336).
  2. The case is decided and closed (phase-18.md section 3.12). Closure does not revoke active grants: section 3.12 steps 1 to 10 contain no `case_acl` update, and the guard `casework.case_acl_guard` only lets `revoked_by` and `revoked_at` change (phase-18.md:427-428).
  3. Day +2 the timer sweep claims the timer (phase-00 `TimerService`, FOR UPDATE SKIP LOCKED) and enqueues `timer_case_acl_expiry`.
  4. The handler locks case C (a row lock, READ COMMITTED), finds the grant still active with `expires_at <= now()`, sets `revoked_at = now()`, and calls `CaseChain::append_event` for `case.acl_expired` (phase-18.md:1337-1339). The case status is never read.
  5. The append writes event `seq = last_seq + 1` and sets `last_seq` and `head_hash` on the sealed case. The seal (`casework.case_seals`, phase-18.md:171-183) keeps the earlier `last_seq` and `head_hash`, so the chain now runs past the sealed head. The `version` is bumped, which also breaks the sealed snapshot of the case.
- Guard search: phase-18.md:1336-1339 has no status test. Grep "E_CASE_SEALED" in phase-18.md section 3.18 or 3.13 finds only the write steps of the other routes (lines 655, 676, 691, 707, 720, 733, 828), not the timer. `casework.case_events_chain_guard` checks only `prev_hash` (phase-17.md:1113-1114). `casework.case_acl_guard` checks only the revoke columns (phase-18.md:337-353). The phase-00 rule (phase-00.md:564-565) names "closed case" but the phase 18 handler text does not implement it. The QA read grant of phase 19 is designed to write no case event on a closed case (phase-19.md:1261), so it is not the same path. No DR found: grep "acl_expired" in docs/plan/research.md returns nothing for a sealed case.
- Severity: MEDIUM (a person would notice a chain event after a seal when verifying the chain, or on the sealed head; no decision or filing is taken; nobody loses a detection).
- Proposed 7.N text: "### 7.N Expiry of a grant on a sealed case" - In the handler `timer_case_acl_expiry` (section 4.1 item 4), after the lock, read `casework.cases.status`. When it is `closed`, set `revoked_at = now()` and `revoked_by = NULL` on the grant and write the audit event `case.acl_expired` only, with no chain event and no `version` bump (the same pattern as the QA read grant of phase 19 section 3.8 step 7). When it is not closed, behave as now. Test: a grant with `expires_at` on a case closed the day before; the timer revokes it; `casework.case_events` has no row with `seq` above the seal's `last_seq`.

### ADV-4-02 An event review that absorbs a new trigger moves `due_at` but leaves the review clock on the old instant   (verdict: FLAW; phase 15, with the phase 00 timers)
- Rule: "Schedule timer `kyc_review_clock {review_id}` at `due_at`" (phase-15.md:1302) and "its handler re-reads the review: when it is still open and past due, it sets `escalated_at`" (phase-15.md:1303-1304); the absorb rule "an open event review of the same party absorbs a new event" (phase-15.md:1310-1311), with the absorbing `due_at = BusinessClock::add(now, review_within)` (phase-15.md:2100-2101).
- Attack:
  1. Party P has an open event review R1 from a level change on day D0: `due_at` = D0 + 5 business days; the timer `kyc_review_clock {R1}` is scheduled at D0 + 5 (phase-15.md:1302).
  2. On day D0 + 1 a second trigger fires for P with `trigger_sla` and `review_within` = 10 business days. The rule-5 absorb (phase-15.md:1310-1311) updates R1: `due_at` = D0 + 11 (the grant of phase-15.md:718 allows `UPDATE (due_at, ...)` on `kyc.kyc_reviews`). No new timer is written: the absorb text names no `TimerService` call, and `TimerService` has only `schedule`, `cancel` and `cancel_for_owner` (phase-00.md:561-562), no reschedule.
  3. D0 + 5: the timer fires (`fire_at <= now()`). The handler reads `due_at` = D0 + 11, so "past due" is false. It does nothing. No timer is left for D0 + 11.
  4. D0 + 11 comes and goes. `escalated_at` stays NULL. The review is in the queue as overdue (phase-15.md:1358, ordered by `due_at`) but no `kyc_review.overdue` audit is written, and the seven-day alert of phase 15 section 6 (phase-15.md:1843) is measured from `due_at`, so it is late.
  5. The reverse order also fails: a second trigger that shortens `due_at` from D0 + 11 to D0 + 3 leaves the timer at D0 + 11; the escalation comes eight days late.
- Guard search: grep "reschedule", "re-arm" and "cancel" in phase-15.md finds no timer re-arm on absorb (phase-15.md:1310-1311 and 2100-2101 name no timer). No trigger or CHECK on `due_at` changes in phase-15.md:280-311 (only `CHECK (date_unknown = (due_at IS NULL))`, phase-15.md:304). The timer handler re-check only covers the closed or cancelled status (phase-15.md:1305). The job `kyc_review_sweep` opens reviews only and does not escalate (phase-15.md:1296-1303, item 2 opens with `open_or_join`). No DR in research.md covers an absorbed review's clock (grep "absorb" in research.md should be checked by the lead).
- Severity: HIGH (the escalation deadline is lost or wrong; the review stays visible in the queue as overdue, so it is not silent).
- Proposed 7.N text: "### 7.N Absorbed event reviews re-arm the clock" - In phase 15 section 3.4 rule 5, when an open event review absorbs a trigger and its `due_at` changes, in the same transaction: `TimerService::cancel_for_owner(tx, 'kyc_review', review_id, 'kyc_review_clock')`, then `TimerService::schedule(tx, NewTimer { owner_kind: 'kyc_review', owner_id: review_id, kind: 'kyc_review_clock', fire_at: new due_at, calendar_id, payload })`. The handler `timer_kyc_review_clock` first compares `due_at` with now(): when `due_at > now()` it schedules the timer again at `due_at` and stops. Test: an event review absorbs a trigger with a later and then an earlier `due_at`; the escalation happens once, at the final `due_at`.

### ADV-4-03 An RFI answer on a closed case appends a chain event after the seal   (verdict: FLAW; phase 19, with phase 18 seal)
- Rule: "write their audit events and no case event, so the seal hash stays the hash of the chain at closure" (phase-19.md:1058); and "A closed case is read-only (section 3.1 invariant I7)." (phase-18.md:852).
- Attack:
  1. Case C is open with an RFI R1 in status `released` (phase-19.md:1098-1113 releases it; nothing in phase 18 section 3.12 closure steps 1 to 10 checks RFIs, so a case can close while an RFI is `released`).
  2. The case is decided and closed (phase 18 section 3.12). Its chain head is sealed (`casework.case_seals`, phase-18.md:171-183).
  3. An analyst or an RFI desk user calls `POST /rfis/{id}/answers` (phase-19.md:1115-1123, Cedar `rfi.answer`). Step 1 locks the case row and the RFI row and accepts status `released` or `answered` (409 otherwise). The step refuses no sealed case.
  4. Steps 3 and 5 insert claims (`claim_state = current`) and set the questions `answered`. Step 6 then runs `case.rfi_answered {rfi_id, count}` as a chain event with no condition on the case status (phase-19.md:1123).
  5. The chain grows after the seal: `last_seq` and `head_hash` change, and the sealed `last_seq` and `head_hash` no longer match the chain head. The RFI status then moves to `answered` on a closed case.
- Guard search: phase-19.md:1115-1119 (step 1: "Status `released` or `answered` (409 `E_NOT_ALLOWED_IN_STATE` otherwise)", no seal test). The only sealed refusals in phase 19 are for drafting (phase-19.md:1064), release (phase-19.md:1103, step 2 (iii)), and watch, hibernation and claim writes listed in the errors table (phase-19.md:1328: "a RFI, a watch, a hibernation or a claim cannot change it") which the answer route does not call. `casework.case_events_chain_guard` checks only `prev_hash` (phase-17.md:1113-1114). No DR found in research.md that allows an answer after closure.
- Severity: MEDIUM (the seal no longer matches the chain; the claims on a closed case are a wrong state a person would notice when the chain is verified; no decision or filing is taken).
- Proposed 7.N text: "### 7.N Answers to an RFI of a sealed case" - In `RfiService::record_answers` (section 3.3), step 1: after the lock, a sealed case (`casework.cases.sealed_at IS NOT NULL`) refuses with 409 `E_CASE_SEALED` (the error of the phase 19 errors table, line 1328), so no claim is written. The refusal matches the phase 18 rule that a closed case is read-only. If the bank wants a correspondent's late answer recorded on a closed case, the route writes the claims and the audit event `rfi.answer_recorded` with no `case.rfi_answered` chain event (the rule of section 3.1, line 1058), and the RFI moves to `answered` only in audit. Test: release an RFI, close the case, then answer it: 409 `E_CASE_SEALED`; the chain head and `last_seq` equal the sealed values.

  2. Merge S into T (phase 17 section 3.6). A1 moves to T (`case_alerts.case_id = T`). P1 is copied to T's `case_parties` but S's rows remain (phase-17.md:1090 is an insert, no delete).
  3. Later, T takes a new alert A2 on party P2 (the target's own subject, not from S). P2 is in T's `case_parties` only.

No DR found covering this (lead to check DR-193 and research.md for "hold" and "merge").

Test: hold S; merge S into T; add a party to T; the next run holds its rows.

- Attack:
  1. A `work_item_due` job for work item W (phase 18) runs its handler, writes `case.work_item_overdue` to the chain and the audit row, and commits.   3. The KYC overdue clock (phase-15.md:1304-1305): "when it is still open and past due, it sets `escalated_at` and audits `kyc_review.overdue`". The handler does not test `escalated_at IS NULL`, so a re-run audits `kyc_review.overdue` again.
- Guard search: phase-17.md:1280-1281 (the touch handler tests that its event does not exist) is the only explicit marker found. phase-19.md:1293 tests the breach state only, which stage 50 does not change. phase-15.md:1304 tests `open` and past due only. phase-18.md:726 tests `state = open` only (the state does not change on the overdue write). The alarm dedup of phase 19 (`insert_live`) covers only the alarm row, not the outbox or the chain. The `timer_committee_report_due` handler is idempotent by its own marker `committee_report_at` (phase-20.md:657), so it is GUARDED.
- Severity: LOW (duplicate notices and chain events; no state is wrong, no breach is recorded twice because of the alarm dedup; a person sees a double entry at most).
- Proposed 7.N text: "### 7.N Overdue handlers write once" - Each overdue handler writes its event only when its own marker is unset, in the same transaction as the write: `timer_work_item_due` checks that no `case.work_item_overdue` event exists for the work item (as phase 17 `alert_touch` does), `timer_breach_stage` checks that no `clock.warning` with the same `owner_id` and `stage` exists in the outbox, and `timer_kyc_review_clock` writes only when `escalated_at IS NULL` (then sets it). Test: run each handler twice; one event is written.

- Proposed 7.N text: "### 7.N The Committee report is delivered, not just requested" - (a) In `timer_committee_report_due` (phase 20 section 3.4), when `committee_report_at` is set, read the letter `committee_report_letter_id`; when its state is not `delivered`, raise `IncidentService::raise(report_missed, freeze)` (the existing incident kind) and audit `freeze.report_undelivered {freeze_id, letter_id}`; no new alarm kind. (b) Phase 21 section 4.5 item 9 `FreezeService::letter_delivered` is the only writer of the delivery to the freeze; the bank decides in Open doubts whether `committee_report_at` means requested or delivered, and the answer goes to a locked decision in research.md. Test: request a committee letter, do not deliver it, run the timer at `committee_report_due_at`: one `report_missed` incident and one `freeze.report_undelivered` audit; deliver the letter first: no incident.

### ADV-4-10 Cancelling a timer that has already fired fails the owner's transaction, so a freeze, filing or work item can become unclosable   (verdict: FLAW; phase 00 timers, with phase 18 work items, phase 20 freeze release and phase 21 filing)
- Rule: "`cancel_for_owner(tx, owner_kind, owner_id, kind)`" (phase-00.md:562) and the table CHECK "`CHECK (fired_at IS NULL OR cancelled_at IS NULL)`" (phase-00.md:149); the cancel callers are a must-happen act: "Cancel the four clocks" in the freeze release (phase-20.md:704), "Cancel the timer `report_filing_target`" in the filing (phase-21.md:903), and "cancels the timer" on work item completion (phase-18.md:722).
- Attack:
  1. Freeze F is `listed` and its `freeze_due` timer fires at `freeze_due_at` (phase-20.md:655: the overdue alarm). The timer row now has `fired_at` set and `cancelled_at` NULL.
  2. The freeze is verified and delisted; M approves the `freeze_release` task (phase-20.md:698-704). `release_freeze` runs `cancel_for_owner(tx, 'freeze', F, 'freeze_due')`.
  3. The phase-00 SQL for the cancel is not written in phase 00 (only the signature is, phase-00.md:437 and 561-562). A plain `UPDATE admin.timers SET cancelled_at = now() WHERE owner_kind = ... AND owner_id = ... AND kind = ...` matches the fired row and violates the CHECK at phase-00.md:149. The `release_freeze` transaction aborts (check_violation). The retry aborts again, because the fired row never changes. The freeze can never be released.
  4. The same happens to a report whose `report_filing_target` alarm fired (phase-21.md:1234: alarm while `signed` or `packaged`): the filing of phase-21.md:903 aborts, so the report can never be marked filed. And to a work item whose `work_item_due` fired (phase-18.md:726): completion aborts (phase-18.md:722).
- Guard search: the cancel SQL is not written in phase 00 (grep "cancel" in phase-00.md returns only lines 437 and 561-562). The partial index `idx_timers_due ... WHERE fired_at IS NULL AND cancelled_at IS NULL` (phase-00.md:151) is for the sweep, not for cancel. The CHECK at phase-00.md:149 is the only guard, and it converts the cancel into a failure rather than a no-op. The phase-00 text "cancelling is an optimisation, the re-check is the guarantee" (phase-00.md:566-567) is the intent, which a failing cancel contradicts. No DR covers this.
- Severity: HIGH (a required act is blocked permanently: a freeze lift, a regulator filing or a work item completion; the failure is an error that the person sees, so nothing is silently wrong, but the regulator filing path is stuck).
- Proposed 7.N text: "### 7.N Cancel only pending timers" - In `TimerService::cancel` and `cancel_for_owner` (phase 00 section 4.1), the statement is `UPDATE admin.timers SET cancelled_at = now() WHERE ... AND fired_at IS NULL AND cancelled_at IS NULL` and returns the number of rows changed. A fired or cancelled timer matches nothing and the call succeeds with 0. Test: fire a `freeze_due` timer, then `cancel_for_owner` on the freeze: no error, the freeze release commits; the same for `report_filing_target` before a filing and `work_item_due` before a completion.

### ADV-4-11 A watch review on a sealed case writes a chain event, against the table that says audit only once closed   (verdict: FLAW; phase 19)
- Rule: "`watch.started`, `watch.triggered`, `watch.expired`, `watch.reviewed` ... while the case is open (`case.watch_started`, `case.watch_reviewed`); audit only once it is closed" (phase-19.md:1348); the general design "the follow-up records of a closed case ... write their audit events and no case event, so the seal hash stays the hash of the chain at closure" (phase-19.md:1058).
- Attack:
  1. Case C is decided with outcome `utr`, filed, and closed and sealed (phase-18.md:845-853 and the filing gate). `RecordDecisionEffect` starts a UTR watch W on C (phase-19.md:1157).
  2. Day +60 the watch expires: `timer_watch_expiry` sets W to `under_review`, writes no work item (C is closed, phase-19.md:1167), and writes audit `watch.expired` (correct).
  3. A `case.decide` holder calls `POST /watches/{id}/review` with `extend` (phase-19.md:1025, 1169-1170). The review step locks the case, then the watch, and runs "Chain `case.watch_reviewed {watch_id, review}`" (phase-19.md:1174), with no test for `sealed_at`.
  4. The chain of the sealed case grows past the seal (the same effect as ADV-4-01 and ADV-4-03), and `extend` sets W to `open` with a new timer on a closed case.
- Guard search: phase-19.md:1169 tests only the state `under_review` ("409 ... `not_due` otherwise"); phase-19.md:1174 has no seal test; phase-19.md:1348 states the audit-only rule for closed cases but the step at 1174 contradicts it. The route's Cedar action `watch.review` (phase-19.md:1025) does not forbid sealed cases. No DR in research.md allows a chain append after closure (grep "watch" in DR-139 and DR-152 for the lead).
- Severity: MEDIUM (the seal stops matching the chain, and a closed case gets a state change; no filing or decision is taken by the review; the same class as ADV-4-03).
- Proposed 7.N text: "### 7.N Watch review of a sealed case" - In `WatchService::review` (section 3.5), after the lock, when the case has `sealed_at` set: write the audit `watch.reviewed` only and no `case.watch_reviewed` chain event; `upgrade_str` on a sealed case is refused with 409 `E_CASE_SEALED` because its work item cannot be opened (phase-18.md:720). Test: review a UTR watch of a closed case with `extend`: the case `last_seq` and `head_hash` equal the sealed values.
