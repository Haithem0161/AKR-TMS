### 7.N The restore namespace takes the cluster rules (V-30-05-a, HIGH; DR-413)
The monthly rehearsal of section 3.9 restores a copy of production data, so its namespace `akr-restore` is under the same controls as `akr` and `akr-mgmt` whenever it exists:
1. `akr-ctl deploy render` writes for `akr-restore` the default deny of ingress and egress and the DNS egress of section 3.3. The only allows are the ones the restore needs: the `restore verify` Job to the scratch PostgreSQL pod on 5432 inside the namespace, and egress from the two to the pgBackRest repository, the object store and OpenBao on the ports `zones.yaml` names for those destinations. No rule lets a pod of `akr` or `akr-mgmt` reach the scratch database, and no rule lets `akr-restore` reach an application pod.
2. `akr-ctl net check --cluster` probes `akr-restore` with the same table and the known-bad probe of section 3.3, and its rows must pass before the restore starts.
3. The Kyverno `verifyImages` policy of section 3.12 covers `akr-restore` in `Enforce` mode.
4. The namespace and its scratch PersistentVolume are deleted when the drill is recorded, so no second copy of the data outlives the rehearsal.
The alternative of section 3.9 (the DR server) is outside the cluster and keeps the DR site rules of section 3.8.

### 7.N The two writers of a system blind period (V-30-07-a, V-30-07-b, V-30-07-d, V-30-07-e, V-30-07-f, MEDIUM; DR-331; DR-413)
Neither writer of section 3.8 has a session, so neither can call `BlindPeriodService::declare` (phase 11: the steward route under Cedar `blind_period.declare`). This phase adds one method to that service and owns it: `BlindPeriodService::record_system(tx, started_at, ended_at, statement) -> Result<Option<BlindPeriod>, AppError>`. Its two callers are `ops_probe` (item 1) and `akr-ctl ha outage record` (item 2). It has no Cedar action, as a job handler and an operator command have none. Both callers connect as `akr_app`, which holds `SELECT, INSERT` on `admin.blind_periods` (phase 11 section 1), so no grant is added. In the caller's transaction the method:
1. Takes `pg_advisory_xact_lock(hashtext('blind_period:system'))` and reads the rows of scope `system` and cause `akr_outage` whose span overlaps the new one. When one exists it writes nothing and returns `None`: the probe logs the id of the row found and still writes `ha.failover_observed`, and the command exits 2 and prints that id. One outage is therefore one row.
2. Refuses a `started_at` earlier than the newest `audit.audit_anchors.anchored_at` and an `ended_at` that is missing, in the future or before `started_at`. The probe never meets the first refusal, because item 1 already takes the later of the two instants.
3. Inserts through `BlindPeriodRepository::open` with scope `system`, cause `akr_outage`, `declared_by` = the system principal (phase 01) and `comment` NULL: the reason is in `statement`, and for the command also in its evidence object. The command's audit event carries the OS user and the PAM session id of the phase 00 rule.
4. Audits `blind_period.opened`, the phase 11 kind for a period that no steward declared.
The probe's `started_at` is an estimate. That departs from the true start that a phase 11 declaration records, which is why `statement` names it as one.

### 7.N The ransomware restore: offline copy, clean environment and rotation (V-30-08-a, V-30-08-b, V-30-08-c, MEDIUM; DR-413)
These rules complete the ransomware paragraph of section 3.9 and item 2 of the DR site list of section 3.8.
1. **Offline copy.** Once a month, after the rehearsal has passed, the bank's operators copy three things to media that are then kept off every network: the pgBackRest repository as it stands after the newest full backup (it is encrypted, phase 00), the newest restic snapshot of the buckets, and the newest OpenBao raft snapshot. The signed release bundle is already on offline media (section 3.11). This is a bank procedure with a line in the rehearsal record, not an AKR-TMS job, and how long the media are kept is the bank's choice (Open doubts 22). No repository is object-locked in this design.
2. **Clean environment.** A host or cluster installed from the offline release bundle, with no route to the production zones until the rotation below is done. The namespace `akr-restore` on the production cluster is not clean after a ransomware event; the monthly rehearsal there proves the restore procedure only.
3. **Order.** Restore OpenBao from its snapshot and unseal it; restore the database from the offline repository; run `akr-ctl restore verify`; rotate; only then open a node to users.
4. **Rotation**, with the means the plan already has, in this order: (a) the AppRole secret ids of section 3.12, issued anew per ceremony (phase 00), with the old ids revoked in OpenBao; (b) the database role passwords, set again by `akr-ctl db provision` (phase 00); (c) the Hydra client secrets, with `akr-ctl identity client rotate` (phase 01); (d) when `pack.assess` is on, a new decision key (`akr-ctl assess keys rotate`) and new gateway certificates (`akr-ctl assess gateway register`, then `revoke` with reason `compromise`; phase 29). The transit keys are rotated by the key ceremony of phase 00 when the bank's security officer finds that OpenBao itself was exposed. One command that runs the whole rotation is not part of this version.
5. **Record.** Each `akr-ctl` step writes the audit event it already has (`service_client.rotated`, `assess.key_activated`, `assess.gateway_registered`, `assess.gateway_revoked`). The evidence file of the run lists the credential kinds rotated in OpenBao and in the database, and the run is recorded with `akr-ctl ops record-restore-drill` (phase 00). No audit kind is added.
@@ END
