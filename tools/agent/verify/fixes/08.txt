### 7.N The code points of scanControls (V-08-08-a, LOW; DR-413)
`scanControls(s)` in the section 3.3 `bidi.ts` row returns offsets only and changes no text. `bidi` flags U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F and U+061C. `zero_width` flags U+200C, U+200D and U+FEFF. The sets are those of research/31-analyst-ux.md section 4.2 rule 4 and of research/22-arabic-name-matching.md section 6.2 (row "Invisible format characters"). Removal for matching is phase 14 N3 (section 3.1).

### 7.N Name flags for bidirectional and zero-width characters (V-08-08-b, MEDIUM; DR-413)
UX-20's flagging as data quality is carried by the `quality_flags` of N-12 (section 3.3), with no new column and no register kind. From phase 11 on the canonical writer sets `bidi_control` on a `party_name` row whose `raw` holds a character of the `bidi` set of phase 08 (section 7+, the code points of scanControls) and `zero_width` on a row whose `raw` holds one of its `zero_width` set; the same two values are set in `quality_flags` of a `counterparty` or `payment_message_party` row whose name holds one. The raw value is stored unchanged. As N-12 says, a flag never lowers a match score. Phase 08's pointer "flagging as data quality arrives with ingestion in phase 11" means this.

### 7.N The transliteration under a name (V-08-11-a, MEDIUM; DR-413)
The `Name` component shows what the source gives. The original is the party's `canon.party_name` row in Arabic or Kurdish script; the transliteration beneath it is the row of the same party and `name_type` with `script = 'lat'`, when the source supplied one, and its source label is the label of that row's `source_field` (the mapped source column, phase 10). A party with no Latin row shows no second line. The product generates no Latin form, so the label `generated` of DESIGN-SYSTEM 7.6 is not used in this plan; phase 14's back-transliteration serves matching only.
