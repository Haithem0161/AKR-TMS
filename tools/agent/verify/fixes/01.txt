### 7.N Service client commands, step by step (V-01-02-a, MEDIUM; DR-413)
The three `akr-ctl identity client` commands of section 3 run as follows (the Hydra admin API through `common::ory`,
`HYDRA_ADMIN_URL`).
1. `client create`: validate (the owner is an active human; scopes within the token allow-list; `--expires` in the
   future, else exit 2 with the field named). Create the Hydra client (grant `client_credentials`, the scopes,
   audience `akr-api`, a generated secret). Then in one transaction insert the `admin.users` row (`kind = 'service'`,
   `hydra_client_id`, `owner_user_id`, `expires_at`) and audit `service_client.created {client_id, owner_user_id,
   scopes, expires_at}`. A failed transaction deletes the Hydra client. The secret is printed once; AKR-TMS stores no
   copy.
2. `client rotate --name`: Hydra replaces the client's secret with a new generated one. The old secret stops working at
   once; access tokens already issued run to their expiry (15 minutes). Audit `service_client.rotated {client_id}`;
   the new secret is printed once. No `admin.users` row changes.
3. `client disable --name`: in one transaction set the principal's `status = 'disabled'` with `disabled_reason =
   'admin'` and audit `service_client.disabled {client_id}`; after commit delete the Hydra client (the order phase 03
   uses when offboarding disables a user's service principals). `authenticate` already refuses a principal that is not
   active, so a failed Hydra call leaves no access and the command can be run again.

### 7.N Actions for heartbeat and logout (V-01-04-a, MEDIUM; DR-413)
The pinned list of section 3 covers every route of this phase but two. `POST /auth/session/heartbeat` uses
`session.read` (it returns the `SessionView` of the caller's own session) and `POST /auth/logout` uses `session.revoke`
on the current session (the same act as `DELETE /me/sessions/{id}` for the current one). No action is added; the
phase 03 retrofit registers both `RouteAction` rows with resource `User(self)`.

### 7.N The token limit is counted under a lock (V-01-05-a, MEDIUM; DR-413)
`TokenService::create`: the `pat.max_per_user` test of step 2 moves into the transaction of step 3. After `consume`
the transaction takes `pg_advisory_xact_lock(hashtext('pat:' || user_id))`, counts the user's active tokens and
answers the same 422 (`limit_reached`) before the insert. Two concurrent creates with two step-up assertions can
then not both pass the count. The other tests of step 2 stay where they are.

### 7.N SP-36 behaviour rules: what ships and what does not (V-01-07-a, MEDIUM; DR-413)
No phase carried SP-36 (the behaviour rule pack of research 30 section 9.3), and this phase's header named phase 24
for it. Decision: SP-36 is partly implemented here and the rest is P2.
1. Shipped: `deploy/siem/use_cases.yaml` (section 3.5) gains the correlation rules that the exported kinds can feed,
   as entries `{id, title, kinds, group_by: actor, window, threshold}`: repeated denied or conflicting attempts
   (`authz.denied`), sign-in anomalies and repeated step-up failures (the SP-18 kinds of phase 01), break-glass use,
   and privileged bursts (role grants, policy activation, key operations). The CI check of section 3.5 covers them: a
   rule may name exported kinds only. The rules run in the bank's SIEM; their recipients are the second line and
   security, never the actor's manager, and the actor is told nothing.
2. Built elsewhere as controls, not as alerts: purpose codes and the conflict check (phase 03), the volume-reduction
   flag and its second approver (phase 04), QA samples (phase 19), and the monthly counts of the control report
   (phase 24 section 3.2).
3. Not built (P2): the rules that need the allowed reads, which are not exported (`authz.allowed` has SIEM "no",
   phase 03): mass lookup, off-hours or off-network access, access with no work reason, snooping on staff or
   relatives, export spikes as an alert, and closure patterns; canary access is P2 already (7.12). A behaviour engine
   inside the product over `access_event` is that P2 item.
