### V-00-05-a  STANDS   (first agent: LOW; refuter: MEDIUM)
- Claim: `Crypto::open` has no error for a decryption or AAD failure.
- Evidence: phase-00.md:587 "`trait Crypto { seal(family, aad, plaintext) -> Sealed; open(family, aad, &Sealed) -> Vec<u8>;`" has no Result on open, so the signature cannot report a failure at all. The same trait block (phase-00.md:587-588) gives `seal`, `keyed_hash`, `sign` and `verify` no Result either. The general error rule does not supply a path: phase-00.md:504 "`Internal` | 500 | `E_INTERNAL` (correlation id only, no detail)" applies only to an error that exists. Later phases read sealed columns with AAD and name no failure: phase-18.md:763 "Decrypt `text_enc` (AAD = proposal id)"; the only decryption failure path in the plan is the evidence stream of phase-02.md:886-888 "Any failure aborts the stream ... before the first byte it is 500 `E_HASH_MISMATCH`", which is the stream construction, not `Crypto::open`. phase-02.md:957 maps a `Crypto` error variant to "503 `E_UNAVAILABLE`", so the plan expects typed crypto errors that the phase 00 port cannot return. Greps that found nothing: `grep -n -i "decrypt_fail|open_fail|seal_fail|crypto_fail|tag mismatch|authentication fail" docs/plan/*.md` (no hit); no phase names a caller of `Crypto::open` with an error mapping.
- Severity reasoning: MEDIUM, above the first agent's LOW. The fault is in the signature, not in wording: the port cannot represent an AAD failure, and every caller of the personal family inherits that. The error rule at phase-00.md:504 does not fill the gap because there is no error value to map.
- Fix: phase 00, section 2 crypto port: give `seal`, `open`, `sign`, `verify` and `keyed_hash` a `Result` over a `CryptoError` defined in that section, with the mapping of its variants to the error catalogue (phase-02.md:957 already maps a crypto failure to 503 `E_UNAVAILABLE`).
